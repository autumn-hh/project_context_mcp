# 本地记忆召回与来源保留

0.10.4 改进 `project_context` 的本地记忆召回，0.11.0 加入来源图谱补充，0.11.1 增加可解释的内容关联并收紧图补充的任务相关性检查。当前版本再加入显式审核的实体与别名召回；CLI 上下文和网页上下文预览复用相同逻辑。

实体整理记录保存在项目 SQLite 的 schema 10 新表，按原有流程迁移旧库；无需重建文本索引或配置模型服务。构建后需要重启使用此源码的 MCP/Web 进程；IDE 的 stdio MCP 由所属客户端重连。直接运行旧进程不会自动加载新逻辑。

## 从 Hindsight 借鉴的思路

参考 Hindsight 官方 [Recall](https://github.com/vectorize-io/hindsight/blob/main/hindsight-docs/docs/developer/retrieval.md) 和 [Observations](https://github.com/vectorize-io/hindsight/blob/main/hindsight-docs/docs/developer/observations.mdx)：记忆应有独立的召回通道，重复结论不应占满上下文，结论必须能追溯原始来源。

本实现使用本地词项匹配和显式确认的实体别名，没有安装 Hindsight，没有接入其 LLM、embedding 或 cross-encoder，也不具备自动理解同义改写、识别矛盾或生成新事实的能力。检索回归使用隔离合成数据。[记忆图谱](memory-graph.md)提供实体、来源与内容关系补充，三路合计最多补充 4 条活跃知识。来源与内容扩展最多使用 5 条命中记忆作为种子，并要求目标正文与任务有关；实体通道使用已确认且不歧义的名称/别名。三路都检查适用范围，并分别以 `entityRecall` 或 `graphRecall` 标明依据。

## 行为

1. **独立检索记忆。** FTS5/BM25 和现有汉字双字索引分别召回，通过 RRF 融合，再按标题/正文词项重合排序。代码片段数量不占用这条记忆通道的名额。中文问句无需覆盖整句的 60% 才能找到短结论；部分常见提问词不参与召回。现有混合搜索的英文近似匹配仍作为补充。
2. **统一适用范围。** 范围检查同时作用于结构化知识和 `relevant`。显式路径按目录边界匹配，`src/storagex` 不属于 `src/storage`；自然语言任务仍可通过主题词和命中的代码/文档路径确定范围。记忆自身的来源路径不能证明自己适用于当前任务。范围是相关性判断，不是访问权限。
3. **精确去重并保留来源。** 只有标题、类型、正文、理由完全相同，且 scope 集合相同的活跃记录才合并展示。代表记录保留所有原有字段，`supportingMemories` 列出其他记录的 ID、来源种类、来源引用和置信度。相同正文但不同标题可能有不同主语，因此也不合并。不会根据重复次数提高置信度。
4. **减少重复上下文。** 已放入 `constraints`、`decisions` 或 `lessons` 的知识不再重复放入 `relevant`。事实、偏好和假设仍可在 `relevant` 召回，并附带 `memoryType`、`scope`、`sourceKind`、`confidence`，保留类型区别。
5. **相关过期提示。** stale/conflicted 记录不作为当前知识返回。警告中最多列出 3 个与任务相关、需要复核的记忆 ID 及状态；通过 `memory_list` 指定状态可检查原始记录。候选、拒绝、删除和已替代记录也不进入活跃召回。
6. **任务摘要继续单独处理。** 默认排除；明确回顾任务或提供任务 ID 时才召回。显式任务 ID 能恢复带文件 scope 的摘要。不同任务的摘要不合并。
7. **来源和内容图补充必须与任务相关。** 已确认实体召回之后的剩余名额，先尝试明确来源、真实任务或替代关系，再尝试内容关联。实体、来源、内容三路合计最多4条，且不重复加入直接命中的记忆。来源/内容目标必须为活跃的非摘要记忆，其标题/正文须与任务具有至少2个独立线索，或1个复合标识符，或1个至少4字的中文线索，同时通过 scope 检查。0.11.0 中仅因共同来源进入的无关内容，现在会被拒绝。
8. **内容关系可以解释。** 记忆之间至少有2个独立的标题/正文词面线索才形成 CONTENT_RELATED；汉字线索至少3字，重叠或嵌套词项不重复计数。通用工作词、角色词、Review模板、来源引用和scope不作为内容关联依据。补充结果的 `graphRecall` 带 `relation: "content-related"`、`possiblyRelated: true`、`sharedTerms` 和两端不超过240字符的连续原文 `excerpts`。这些字段表示“可能相关”，不证明依赖、支持、因果或观点一致，不提高原记忆置信度。
9. **实体别名须先审核。** 本地 `memory_knowledge` 候选文档提供实体名称、类型、别名和连续原文证据，明确接受后才参与召回。名称/别名需唯一指向一个实体；小于3字符不用于实体扩展，英文标识按词边界匹配。命中的记忆仍须通过 scope，保持活跃非摘要且原文哈希有效；同一记忆多份 accepted 冲突会被排除。该通道可以利用显式别名找到正文没有使用该别名的记忆，不猜测同义词。
10. **实体依据单独返回。** `entityRecall` 包含 entityId、name、matchedName、annotationId、quote 及有界关系说明，能回到具体审核记录和原文。清单截断时无法可靠检查别名歧义，会保守停止实体补充并在上下文 warnings 中提示。

以上召回操作仅组装读取结果，不修改、删除、自动接受或替代数据库中的记忆。实体文档的提交与审核通过单独 MCP/Web 操作执行。`memory_remember` 可选 knowledge，`memory_candidate_accept` 可传与 review 同级的 knowledge；记忆写入和 pending 实体候选原子保存，但实体仍需单独接受。来源文件是否变化仍由原有索引和段落指纹检查决定，实体文档另外校验完整标题/正文哈希。

网页“记忆关系”提供 knowledge、evidence、entities 三种视图。实体节点只出现在第三种视图；图下可分页审核候选，原文改变后显示待复核。详见[本地记忆图谱](memory-graph.md)中的数据结构、审核流程和 API 示例。

## 预算与限制

- 记忆查询最多使用 64 个词项。每个召回通道以 128 条为一页；范围筛选不足时继续查找，最多读取 4 页（512 条候选），每路最多保留 128 条适用记录参与融合，默认返回 32 条。
- 这是有界检索；超过这些范围的大量同关键词记录、重复记录仍可能挤出旧知识。语义不同但词面相似的内容可能误召回；同义表达、跨语言查询、过长问题可能漏召回。不会把词项重合分数当作事实可信度。
- 实体、来源和内容补充合计最多4条；来源/内容图最多取5条命中记忆为种子。内容候选的FTS和汉字索引各有128条上限，只检查标题与正文的前8000字符范围。它不会扫描全库比较所有记忆，不保证发现所有关联。图视图中的相邻关系还须通过对应召回条件和范围检查才能进入上下文。
- 实体召回先扫描最多16,384个名称/别名、100万字符，选择任务实际提及的最多8个名称，再分别读取对应名称的最多100份有效标注、200个实体。无关注解超过100份不会关闭全局实体召回。某名称的所有者清单不完整时，只跳过该名称并提示，不对部分清单推断唯一性。名称扫描或结果触顶仍可能漏召回；SQL处理成本不是恒定上限。
- 上下文继续使用原有估算 Token 预算。紧预算优先裁剪额外重复来源，保留代表记录的来源；裁剪发生时 `budget.truncated` 为 true。原有正文裁剪及分组淘汰机制仍生效；扩大 `budgetTokens` 可读取更多内容。极小预算可能不足以保留完整记录。
- 本地任务上下文使用上述记忆与图补充通道；通用 `project_search` 的代码/图谱搜索及可选 embedding 配置、远程团队检索保持原有行为。
- schema 10 知识包包含实体整理记录，新版仍可恢复不含该表的 schema 9 旧包。多机同步需参与设备全部升级；冲突记录不会自动进入有效图或召回，仍需明确复核。现有备份和本地数据边界详见图谱文档。

## 0.10.4 历史回归与验证

`tests/memory-context.test.ts` 使用独立内存 SQLite，不读取用户记忆或云端数据。最初 8 项行为断言在旧实现均失败，首轮改进后全部通过；随后补充主题区分、任务摘要恢复、状态与名额、类型来源、预算、分页和路径边界回归。

| 用例 | 旧实现 | 新实现 |
| --- | --- | --- |
| 1 条旧决定、80 条无关新记忆、120 段匹配代码 | 决定漏召回 | 决定进入上下文 |
| 中文长问句寻找旧备份决定 | 漏召回 | 找回相应决定 |
| 同一决定进入结构化字段和通用命中 | 正文重复两份 | 正文一份 |
| 完全相同知识、不同来源 | 多条占位 | 合并展示，来源可追溯 |
| 不适用模块的规则有匹配关键词/自身来源 | 可绕过范围筛选 | 排除 |
| 目录范围命中子文件 | 可能漏掉 | 按路径边界匹配 |
| 相关过期记录 | 仅有总数提示 | 提供具体待复核 ID |

验证命令：

```sh
npx vitest run tests/memory-context.test.ts tests/mcp.test.ts
npm run typecheck
npm test
npm run eval -- --iterations=5
npm run build
```

专项用例是明确问题的回归验证，不代表真实大规模项目的整体召回率，也不是与 Hindsight 的性能对比。既有质量评估使用另一组合成项目，结果应单独报告。

2026-10-30 的0.10.4本地验证：15 项记忆专项与 5 项 MCP 测试通过；全量 40 文件 / 279 项通过；typecheck、build、分发清单检查通过。独立启动编译后的 0.10.4 stdio MCP，中文问句返回 1 条结论、保留 2 份来源，数据库仍有 2 条原记忆。既有 eval 的 Recall@5、上下文必需召回率、已选记忆准确率均为 1；当次最终运行 MRR=0.926，前一次为0.870，差异来自既有通用搜索的并列排序，不能算作图谱或内容关联改进收益。0.11.0 的图谱历史验收另见[记忆图谱说明](memory-graph.md)。
